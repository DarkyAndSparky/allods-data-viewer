# Allods Data Viewer: детальный роадмап и макет проекта

Версия от 2026-11-09. Документ экспортирован из рабочего планировочного документа; три схемы (архитектура, этапы, макет интерфейса) в текстовый файл не переносятся, они остались в онлайн-версии.

Подробности: [структура репозитория и ядро](ARCHITECTURE.md), [форматы](formats/README.md), [список упущений](GAPS.md), [какие образцы нужны](SAMPLES_REQUEST.md), [правила разработки](engineering/WORKFLOW.md), [решения](adr/).

## 1. Видение

Allods Data Viewer читает, показывает, извлекает и конвертирует все данные клиента Allods Online на Windows и Linux, а потом умеет собрать изменённые файлы в **новый** `.pak`. Оригиналы клиента программа не трогает.

**Для кого**

- Переводчики и моддеры текстов: таблица ключей и текстов, поиск, экспорт.
- Исследователи данных: базы `.bin`, квесты, предметы, экспорт в JSON и XML.
- Те, кто работает с ресурсами: текстуры в PNG, модели в glTF, звук в WAV, OGG и MP3, видео.
- Авторы фанатских проектов, которым нужны проверенные описания форматов.

**Чем отличаемся от AODataViewer**

- Нет закрытого движка: форматы читает собственный код на Rust, а не NeoAxis.
- Ошибки возвращаются как значения, файлы читаются потоком. Нет тихих падений и 64 МБ на каждое чтение.
- Есть консольная программа для пакетной работы, а не только окно.
- Добавлены звук, видео, оба формата `.loc`, базы `.bin`, модели с текстурами, упаковка.
- Лицензия MIT, код и описания форматов открыты.

**Границы.** Не меняем файлы клиента на месте, не распространяем ассеты игры, не обходим защиту. Упаковка пишет только новые файлы.

**Как поймём, что получилось (цели, не обещания)**

- Открыть любой `.pak` клиента и получить дерево файлов без ошибок.
- Найти строку по ключу или тексту во всех `.loc` за доли секунды.
- Выгрузить весь звук клиента в WAV или MP3 одной командой.
- Увидеть модель сразу с наложенными текстурами.

## 2. Принципы и правила

Все решения ниже проверяются этими восьмью правилами.

1. **Только чтение оригиналов.** Запись всегда идёт в новый файл в другой папке, упаковка никогда не перезаписывает файл клиента.
2. **Формат — это факт, код — нет.** Описываем формат своими словами в `docs/formats`, потом пишем код по описанию. Статусы: `unknown`, `draft`, `verified`. Статус `verified` ставим только после прогона по реальным файлам.
3. **Лицензии источников.** Код из MIT и Apache-2.0 проектов можно портировать с записью в `NOTICE`. Код из AGPL и проектов без лицензии не копируем, берём только факты о форматах.
4. **Зависимости текущего года.** Прямые зависимости и инструменты — релизы 2026 года, дату проверяем по реестру перед добавлением. Переходные — последние доступные.
5. **Ни одного ассета игры в репозитории.** Тесты строят синтетические данные в коде. Образцы пользователя лежат вне репозитория (`/samples/` в `.gitignore`).
6. **Ошибки — значения, не паника.** Без `unsafe`, без загрузки всего файла в память, повреждённый вход не должен ронять программу.
7. **Windows и Linux на равных.** CI гоняет тесты на обеих системах.
8. **Работа без привязки к IDE.** Проект не зависит от настроек редактора, разработка идёт в полноценной IDE (например RustRover), не в VS Code.

## 3. Что мы знаем о данных

Два формата проверены на реальных файлах (`.pak`, старый `.loc`), остальное — черновики или пока неизвестно.

| Формат | Статус | Что известно | Откуда | Что нужно |
| --- | --- | --- | --- | --- |
| `.pak` | verified | Обычный ZIP. Записи stored или deflate, у каждой CRC32. Поверх данных может лежать ещё слой zlib | Наши образцы | Правило для повторяющихся путей |
| `.loc`, старый (32 бит) | verified | Таблица ключей (UTF-8) и текстов (UTF-16). Проверено на 21 693, 150 587 и 301 590 записях, один дубль ключа | Наши образцы | — |
| `.loc`, новый (64 бит) | draft | Сигнатура `0x162E0F62`, 566 294 записи в обоих файлах (рус. и англ.), дескрипторы не расшифрованы | Наши образцы | Декодирование дескрипторов |
| Текстуры `.bin` | draft | zlib, внутри куски (id, размер, данные), мипы от меньшего к большему; ширина, высота и тип сжатия лежат в базе | EditorTools (MIT) | Образцы и запись из базы |
| Базы `.bin` (V1, V2 x86/x64) | draft | Цепочка кусков, слепок памяти C++ объектов, таблица исправления указателей, структуры зависят от версии клиента | EditorTools (MIT) | `pack.bin` нужной версии |
| `.xdb` | draft | Текстовое представление записей базы | AOParser (MIT), EditorTools | Образец |
| Звук `.fsb` | draft | Банк FMOD, версия и кодек неизвестны | Набор BSBtoFSB | Образцы |
| Звук `.bsb` | draft | zlib, после распаковки отбросить первые 4 байта и останется `.fsb` | Набор BSBtoFSB | Образцы |
| Видео `.ogv` | draft | Ogg, лежит в ZIP без сжатия | Наш образец (скриншот архива) | Один небольшой файл |
| Шрифт `.ttf` | verified | Обычный TrueType, внутри имя AllodsWest, 316 глифов, кириллица есть | Наш образец | — |
| Модели | unknown | В базах есть описание вершин и уровней детализации, значит часть данных лежит там | EditorTools (намёк) | Образцы |
| Материалы (связь модели с текстурами) | unknown |  |  | Образцы |
| `.tga`, `.psd`, `.lua`, `.cur`, `.hlsl`, `.bev`, `.eh`, `.ej` | unknown | Только имена расширений из списка ссылок в базах | EditorTools | Образцы |

## 4. Архитектура

&#91;embedded content: архитектура · ядро и две оболочки\]

Ядро ничего не знает об интерфейсе: CLI и приложение вызывают одни и те же функции. Конвертеры пишут результат в новые файлы, упаковщик собирает новый `.pak`.

**Правила ядра**

- Каждый читатель принимает `Read + Seek` и отдаёт данные потоком, поэтому размер архива не влияет на память.
- Ошибки формата возвращаются значениями с указанием файла и смещения. Паники на повреждённых данных считаются багом.
- Формат определяется по содержимому, а не по расширению. Неизвестное — это явный результат «формат не распознан».
- Версии клиента описываются таблицами, а не условиями в коде: новая версия добавляет данные, а не ветки.
- Новый формат подключается как отдельный модуль со своим описанием в `docs/formats` и своими тестами.
- Web-интерфейс не читает файлы сам: всё идёт через команды ядра. Те же функции годятся для запуска без Tauri.

## 5. Этапы

M0 (скелет, брендинг, доки) готов. Размер: S — несколько дней работы, M — около недели, L — несколько недель, XL — месяц и больше. Календарных дат нет: они зависят от того, какие образцы придут. Каждый этап закрывается только когда выполнены все пункты «Готово, когда».

&#91;embedded content: дорожная карта · 4 фазы, 11 этапов\]

Фазы не привязаны к датам: ромб под фазой — её критерий выхода, дальше идём только после него.

### M1. Архивы и локализация (M)

- **Цель:** читать `.pak` и `.loc`, искать по ключам и текстам, извлекать файлы.
- **Задачи:**
  - слой чтения `Read + Seek`, потоковая распаковка ZIP с проверкой CRC32;
  - прозрачный второй слой zlib;
  - виртуальная файловая система поверх нескольких паков (`data/Packs`), правило для повторяющихся путей;
  - чтение старого `.loc` по подтверждённой спецификации;
  - новый `.loc`: скрипт-разборщик, спецификация, затем читатель;
  - команды `list`, `extract`, `search`, `loc dump`.
- **Готово, когда:** три старых `.loc` дают 21 693, 150 587 и 301 590 записей; `extract` выдаёт файл с той же CRC32, что в архиве; тесты на синтетических паках зелёные на Windows и Linux.
- **Нужно от вас:** список паков из `Packs`, ещё несколько небольших паков.
- **Риски:** новый `.loc` может содержать индексы и сжатие; повторяющиеся пути в разных паках.

### M2. Текстуры (M)

- **Цель:** текстура `.bin` в DDS и PNG, просмотр `.tga`.
- **Задачи:** чтение цепочки мипов (zlib, куски до `id = 0`, порядок развёрнут); сборка заголовка DDS; собственный декодер блочных форматов (DXT1, DXT3, DXT5) в RGBA; запасной вариант, когда размеры указаны вручную (`--size 512x512`).
- **Готово, когда:** пять образцов дают правильные PNG (смотрим глазами), DDS открывается в стороннем просмотрщике.
- **Нужно от вас:** пара текстур `.bin` и та же запись из базы (или известные размеры).
- **Риски:** без базы размер неизвестен, его придётся угадывать по длине цепочки мипов — такие догадки помечаем как недостоверные.

### M3. Звук (L)

- **Цель:** открывать `.fsb` и `.bsb`, слушать на лету, выгружать массово в WAV, OGG и MP3.
- **Задачи:**
  - разобрать версию FSB и кодеки по образцам, описать в `docs/formats/media.md`;
  - обёртка `.bsb` (zlib, без первых 4 байт);
  - список потоков банка: имя, длительность, частота, каналы, кодек;
  - декодирование в PCM, запись WAV; если поток Vorbis — выгрузка в OGG без перекодирования;
  - MP3: см. раздел 9 (решение по кодеру);
  - пакетный экспорт с параллелизмом и шаблоном имён файлов.
- **Готово, когда:** все потоки из образцов выгружаются, длительность в файле совпадает с метаданными банка, WAV играет без щёлков.
- **Нужно от вас:** 2–3 маленьких `.fsb` и 2–3 `.bsb`, лучше разных по типу (музыка, эффекты, речь).
- **Риски:** в банках FMOD Vorbis хранит заголовки отдельно, потребуется их восстановление (это мы проверим на образцах, сейчас это предположение); лицензия MP3-кодера.

### M4. Видео (S)

- **Цель:** достать `.ogv` и посмотреть их.
- **Задачи:** потоковое извлечение с проверкой CRC32; кнопка «Открыть в системном проигрывателе»; информация о кодеках и длительности. Встроенное воспроизведение решаем после проверки образца: Theora в встроенных браузерах ненадёжен, варианты — необязательный транскод через ffmpeg или свой декодер.
- **Готово, когда:** все 7 файлов из вашего архива извлекаются с верной CRC32 и открываются в проигрывателе.
- **Нужно от вас:** один небольшой `.ogv`; ответ, что вы называли «импортом» видео (замена файла в новом паке или что-то ещё).
- **Риски:** замена видео изменит размер файла в паке, клиент может не принять пак, это проверяется только у вас в игре.

### M5. Настольное приложение (L)

- **Цель:** окно с деревом файлов и предпросмотром всего, что умеет ядро к этому моменту.
- **Задачи:**
  - оболочка Tauri 2, обмен с ядром через команды, без лишних прав доступа к файлам;
  - дерево с ленивой загрузкой и поиском;
  - панели предпросмотра: текст, таблица `.loc`, текстура, звук с плеером, видео, шестнадцатеричный просмотр;
  - окно «О программе» (уже есть в веб-части), настройки: папка клиента, язык, шрифт;
  - иконки и установщики для Windows и Linux.
- **Готово, когда:** приложение открывает папку клиента, показывает дерево и предпросмотр текстов, текстур и звука; установщик ставится и запускается на чистой Windows и чистом Linux.
- **Риски:** встроенный браузер отличается на разных системах (WebView2 в Windows, WebKitGTK в Linux): WebGL и аудио нужно проверять на обеих.

### M6. Базы `.bin` (XL)

- **Цель:** читать базы и выгружать в JSON и XML.
- **Задачи:** разбор кусков и метаданных (V1 и V2); определение версии по хэшу заголовка; таблица исправления указателей; структуры по версиям. Сначала список файлов и структур в базе, потом полный экспорт. Код из EditorTools (MIT) портируется с записью в `NOTICE`; структуры (около 6 000 файлов) лучше генерировать из данных, а не переписывать вручную.
- **Готово, когда:** вывод нашего экспорта совпадает с выводом эталонного инструмента на тех же файлах (сравнение выводов).
- **Нужно от вас:** `pack.bin` и версия клиента.
- **Риски:** новые версии клиента меняют структуры; референс поддерживает не все версии (есть таблица поддерживаемых).

### M7. Модели (L)

- **Цель:** геометрия моделей в glTF, который открывается в Blender.
- **Задачи:** разбор формата по образцам (заголовок, буферы вершин и индексов, уровни детализации); в справочном проекте есть описания вершинных элементов и уровней детализации, значит часть метаданных модели хранится в базе; запись glTF.
- **Готово, когда:** минимум три разные модели открываются в Blender без искажений.
- **Нужно от вас:** 2–3 модели разного типа (персонаж, предмет, здание) и расширения их файлов.
- **Риски:** формат неизвестен, это исследовательский этап, его срок следует считать оценкой с большой погрешностью.

### M8. Материалы (M)

- **Цель:** узнать, какие текстуры надо наложить на какую часть модели.
- **Задачи:** найти, где хранится связь (в базе, в файле модели или по имени); записать правило в `docs/formats`; реализовать привязку; glTF с текстурами.
- **Готово, когда:** три модели экспортируются с правильными текстурами на нужных частях.
- **Нужно от вас:** модели из M7 вместе со всеми файлами, которые они используют.

### M9. 3D-просмотр (M)

- **Цель:** модель в приложении с наложенными текстурами.
- **Задачи:** Three.js, вращение и масштаб, переключение уровней детализации, каркас и плоская заливка, сетка, кнопка «экспорт в glTF».
- **Готово, когда:** модель из M8 видна одинаково в Windows и Linux.
- **Риски:** WebGL в WebKitGTK бывает нестабилен, нужен запасной режим.

### M10. Упаковка в новый `.pak` (M)

- **Цель:** собрать `.pak` из папки, не трогая оригиналы.
- **Задачи:** запись ZIP с выбором stored или deflate и CRC32; для файлов, где требуется, дополнительный слой zlib; запись `.loc` обратно из таблицы (переводы); запись видео без перекодирования; предупреждение о правилах игры и апдейтере; отказ перезаписывать существующий файл.
- **Готово, когда:** круговой тест «распаковать, упаковать, сравнить содержимое» проходит; вы проверили в клиенте, что новый пак принят.
- **Риски:** клиент может требовать особый порядок записей или проверять размеры паков; обратная упаковка звука в FSB требует кодировщика и не входит в этот этап.

### M11. Скелеты и анимации (L)

- **Цель:** показывать анимации персонажей и экспортировать их в glTF.
- **Задачи и критерии:** определим после M7, когда станет ясно, как хранится скелет. Пока неизвестно ничего.

## 6. Макет интерфейса

&#91;embedded content: макет · главное окно\]

Это схема расположения, а не дизайн: цвета и пропорции уточним при реализации M5. Слева дерево файлов, в центре предпросмотр выбранного файла, справа свойства и действия, внизу строка состояния.

**Что показываем для каждого типа файла**

| Тип файла | Предпросмотр | Действия |
| --- | --- | --- |
| `.loc` | Таблица ключей и текстов, поиск, подсветка совпадений | Копировать, экспорт в CSV и JSON |
| Текстура | Картинка, масштаб, фон «шахматка», размеры и число мипов | Сохранить PNG или DDS |
| Звук | Список потоков, плеер (пуск, пауза, перемотка, громкость) | Экспорт WAV, OGG, MP3, пакетный экспорт банка |
| Видео | Кодеки, длительность, кнопка открытия | Извлечь, открыть в системном проигрывателе |
| Модель | 3D-вид, уровни детализации, каркас | Экспорт glTF |
| База `.bin` | Дерево структур, поиск по имени | Экспорт JSON и XML |
| Неизвестный тип | Шестнадцатеричный вид и размер | Извлечь как есть |

**Общие решения**

- **Тема:** тёмная, цвета из логотипа (золото, красный, тёмный фон). Светлую тему добавим позже, если будут просьбы.
- **Шрифт:** игровой `AllodsWest`, если он установлен у пользователя, иначе системный. Для ключей, путей и hex — моноширинный.
- **Язык:** русский и английский, выбор по языку системы, переключатель в настройках.
- **Окно «О программе»:** уже сделано в веб-части (логотип, версия, лицензия, ссылка, оговорка о правах).
- **Другие экраны:** настройки (папка клиента, язык, путь к внешним программам), диалог экспорта (формат, папка, шаблон имён), пустое состояние «выберите папку клиента», экран ошибки с подробностями для багрепорта.
- **Доступность:** всё доступно с клавиатуры, видимое кольцо фокуса, контраст не ниже стандартного.

## 7. Спецификация CLI

Консольная программа называется `adv`. Она тонкая обёртка над ядром: всё, что умеет CLI, умеет и приложение. Команды появляются по этапам из раздела 5.

| Команда | Что делает | Этап |
| --- | --- | --- |
| `adv info <файл>` | Определяет формат и показывает заголовок | M1 |
| `adv list <pak \| папка> [--glob шаблон]` | Список файлов с размерами и CRC32 | M1 |
| `adv extract <источник> <путь \| шаблон> -o <папка> [--raw]` | Извлекает файлы; `--raw` не снимает слой zlib | M1 |
| `adv search <папка> <текст> [--keys \| --text]` | Поиск по ключам и текстам `.loc` | M1 |
| `adv loc dump <файл> --format csv \| json` | Выгрузка всех записей | M1 |
| `adv tex convert <файл> --format png \| dds [--size ШxВ]` | Конвертация текстуры | M2 |
| `adv audio list <банк>` | Потоки банка | M3 |
| `adv audio export <банк \| папка> --format wav \| ogg \| mp3 -o <папка>` | Массовый экспорт звука | M3 |
| `adv video extract <pak> -o <папка>` | Извлечение `.ogv` | M4 |
| `adv db info \| list \| export <база>` | Работа с базами `.bin` | M6 |
| `adv model export <модель> --format gltf` | Экспорт модели | M7–M8 |
| `adv pack <папка> -o <новый.pak> [--store \| --deflate]` | Сборка нового архива | M10 |

**Общие правила**

- Флаги всех команд: `--json` (машинный вывод), `--quiet`, `--verbose`, `--threads N`.
- Коды возврата: 0 — всё в порядке, 1 — ошибка, 2 — часть элементов не обработана (список в отчёте).
- Выводная папка не должна совпадать с папкой клиента, существующие файлы не перезаписываются без `--overwrite`.
- Длинные операции показывают прогресс и в конце выводят сводку: сколько готово, сколько пропущено и почему.

Примеры вызовов:

```
adv list "C:\Games\Allods\data\Packs" --glob "*.loc"
adv search "C:\Games\Allods\data\Packs" "Аксинья" --text
adv audio export sounds\ --format wav -o out\audio --threads 4
```

## 8. Тестирование и качество

Репозиторий не содержит данных игры, поэтому проверки делятся на три уровня.

1. **Синтетические тесты (в репозитории, идут в CI).** Маленькие файлы строятся прямо в тесте: ZIP с двойным сжатием, `.loc` на пару записей, текстура из одного блока. Каждый читатель имеет тест на повреждённый вход: ожидается ошибка, не паника.
2. **Образцы пользователя (вне репозитория).** Тесты читают папку из переменной `ADV_SAMPLES`. Если переменной нет, они пропускаются. Проверяют контрольные числа (число записей, CRC32, длительность звука) и позволяют повышать статус формата до `verified`.
3. **Сравнение с эталоном.** Для баз `.bin` вывод сравнивается с выводом справочного MIT-инструмента на тех же файлах.

**Дополнительно**

- Круговые тесты для упаковки: распаковать, упаковать, распаковать снова, сравнить.
- Фаззинг читателей (`cargo-fuzz`) для `.pak`, `.loc`, банков звука и баз.
- Снимки вывода CLI для стабильных команд.
- Бюджет памяти: чтение одного файла не должно зависеть от размера архива. Поиск по 300 тысячам записей — цель доли секунды, измеряем отдельным тестом.
- Интерфейс: `vitest` для логики, скриншоты Playwright для ключевых экранов (начиная с M5).

**CI на каждый push:** `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` на Ubuntu и Windows; в веб-части `typecheck`, `test`, `build`.

## 9. Технологии и зависимости

Это кандидаты, а не решения. Лицензии тут указаны по моему примерному знанию и не проверялись по реестру. Перед добавлением каждой зависимости проверяем два факта: релиз вышел в 2026 году и лицензия совместима с MIT.

| Область | Кандидат | Замечания |
| --- | --- | --- |
| ZIP | `zip` | Чтение и запись, есть stored и deflate |
| zlib, deflate | `flate2` с чисто растовым бэкендом | Для слоя zlib поверх данных |
| CRC32 | `crc32fast` |  |
| PNG | `png` |  |
| Блочные текстуры | собственный декодер | DXT1, DXT3 и DXT5 просты, лишняя зависимость не нужна |
| WAV | собственная запись заголовка | Тривиальный формат |
| Vorbis (декодирование) | `lewton` или `symphonia` | У `symphonia` лицензия MPL, это надо проверить |
| MP3 (кодирование) | внешний `lame` или `ffmpeg` | LAME — LGPL, вшивать его в MIT-программу сложно. План: WAV и OGG встроены, MP3 через внешнюю программу, которую программа находит в PATH или по пути из настроек. Чисто растовый MP3-кодер рассмотрим, если найдётся свежий с подходящей лицензией |
| Theora (видео) | внешний `ffmpeg` или системный проигрыватель | Готового чисто растового декодера я не знаю, решим после образца |
| glTF | `serde_json` и собственная запись | Формат прост и описан публично |

**Правило года.** Прямые зависимости и инструменты — релизы 2026 года. Если нужная библиотека в 2026 году не выпускалась, мы не берём её без вашего решения и записи в документации. При этом собственная реализация простых вещей (DXT, WAV, glTF) дешевле лишней зависимости.

## 10. Юридическое и этическое

Я не юрист, ниже — практические правила для открытого фанатского инструмента, не юридическая консультация.

- **Название.** «Аллоды» — товарный знак правообладателей. Название «Allods Data Viewer» описывает, с какой игрой работает инструмент, поэтому в README и в окне «О программе» стоит оговорка «не связано с разработчиками». Риск претензии от правообладателей остаётся; если она придёт, проект переименуется нейтрально (потому код и крейты уже не зависят от названия).
- **Шрифт `Allods.ttf`.** В файле сказано: © 2008 Nival Online, все права защищены. В репозиторий и в сборки для других людей его не кладём. На своем компьютере пользователь устанавливает его сам, без него интерфейс использует системный шрифт. Если нужен вид похожий на игровой в официальной сборке, нужен свободный шрифт с кириллицей (лицензия OFL), выберем его отдельно.
- **Ассеты игры.** Тексты, текстуры, звук, видео и модели не попадают в репозиторий: ни как тесты, ни как скриншоты в документации. Скриншоты для README делаем на синтетических данных.
- **Упаковка.** Подмена файлов клиента может нарушать правила игры и ломать апдейтер. Программа пишет только новые файлы и перед первой упаковкой показывает предупреждение. Ответственность за замену файлов в клиенте несёт пользователь.
- **Чужой код.** Код из MIT и Apache-2.0 берём с записью в `NOTICE`. Код AGPL (клиент SarnautCore) и проекты без лицензии (AODataViewer) не копируем.
- **Логотип.** Добавлен в репозиторий под вашей ответственностью: нужно подтвердить, что у вас есть права на его использование и распространение под выбранной лицензией (логотип можно оставить под отдельными условиями, не MIT). В логотипе надпись «Allods Data Viewer», поэтому он живёт вместе с названием.

## 11. Риски, открытые вопросы и образцы

Самый большой риск — данные, которых у нас ещё нет: модели, звук и новый `.loc`. Оценки вероятности — моё суждение, а не измерение.

| Риск | Вероятность | Что делаем |
| --- | --- | --- |
| Формат моделей окажется сложным или завязанным на базу | Высокая | Начинаем с образцов, не обещаем сроки до M7 |
| Новый `.loc` содержит сжатие или индексы | Средняя | Скрипт-разборщик до кода читателя, сравнение русского и английского файлов (структура одинаковая) |
| Звук FMOD закодирован нестандартно | Средняя | Выясняем по образцам; если кодек неизвестен, работаем только с поддерживаемыми и явно пишем об этом |
| Theora не играется во встроенном браузере | Высокая | Системный проигрыватель сразу, встроенный — позже через транскод |
| WebGL в WebKitGTK на Linux | Средняя | Проверяем на ранней сборке, держим запасной режим |
| Клиент не примет собранный `.pak` | Средняя | Круговой тест, запись только новых файлов, проверка в игре делает пользователь |
| Претензия правообладателей к названию | Низкая или средняя | Оговорки в документации, нейтральные имена крейтов |
| Структуры баз устаревают с новыми версиями клиента | Высокая | Таблица поддерживаемых версий, чёткое сообщение «версия не поддерживается» вместо тихих ошибок |

## 12. Выпуск и ближайшие шаги

**Выпуск**

- Версии по SemVer, до M5 только `0.x`. `CHANGELOG.md` в формате Keep a Changelog.
- Релиз собирает CI по тегу и публикует в GitHub Releases.
- До M5 выпускаем только консольные переносимые архивы (zip для Windows, tar.gz для Linux).
- После M5: установщик для Windows и пакеты для Linux (AppImage и deb). Подпись кода пока не планируем, поэтому в Windows будет предупреждение SmartScreen.
- Dependabot открывает еженедельные просьбы на обновление зависимостей.

**Ближайшие шаги**

1. Создать репозиторий `allods-data-viewer` и залить архив `allods-data-viewer-m0-v3.zip`.
2. Прислать образцы из чек-листа в разделе 11.
3. Утвердить макет интерфейса (раздел 6) и порядок этапов (раздел 5).
4. Расшифровать новый `.loc` по уже лежащим файлам: это не зависит от других образцов.
5. Начать M1, когда пункты 1–4 закрыты.
