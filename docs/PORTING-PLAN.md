## 0. Главное за одну страницу

1. **Самый ценный источник — `allods-resource-exporter` (Python, MIT, 5289 строк, клиент 1.1.02.0).** Это единственный из инструментов, который доходит до готового результата: меши, текстуры, скелет, клипы, частицы, коллизии, террейн, сцена, UI, звуки персонажей по XML. Он читает форматы, которые у нас пока `draft` или `not started`: материальные дорожки анимации (UV-скролл, прозрачность), кэш частиц, плоскостные коллизионные меши, террейн (`terrainDump`), структуру скелета клиента 1.1.
2. **`AllodsOnlineEditorTools` (C#, MIT) даёт то, чего нет больше нигде: типизированные раскладки структур базы ресурсов для пяти версий клиента** (1.1.02.0 — 616 структур, 3.0 — 808, 4.0.02.43 — 1022, 7.0.00.76 — 1285, 14.0.01.71 — 1462) и сериализаторы в JSON (jdb) и XML (xdb). Генератор структур в репозиторий не вошёл (`StructCodeGeneration` отсутствует), но готовые `[FieldOffset]`-описания лежат в `.cs` и разбираются обычным парсером.
3. **Для текущего клиента (18.0, x64, V2) готовых раскладок нет ни у кого.** EditorTools распознаёт 17.0.01.55 только как «parse only». Поэтому для него нужен собственный вывод раскладок. Источники такого вывода у нас есть: `types.xml` (9,7 МБ, схема полей с `ChunkID`) в `AllodsLegacy-server-data` и PDB-символы в `ao-helper` (см. §6, этап P4).
4. **Ни один из инструментов не пишет игровые файлы.** Нет `.pak` writer, нет texture import (`SaveAsBin` в EditorTools бросает `NotImplementedException`, команда DDS-import скрыта), нет `.loc` writer, нет записи базы (в EditorTools есть заготовка `BinaryStructWriter`, но в CLI она не подключена). «Запаковка» целиком наша работа; чужого кода под неё нет, есть только факты форматов.
5. **`AllodsV4_Developer` портировать нельзя и не нужно:** это внедряемая в процесс клиента DLL (подмена системного времени, перехват `CreateFile`, правка кода по адресу, модули `Protector` и `Crasher`). Это прямо попадает под «Out of scope» в `docs/ROADMAP.md` («ничего, что обходит защиту игры»).
6. **Расхождения между источниками** (см. §9). Флаг `vb32` теперь закрыт прогоном на реальном клиенте 1.1.00.41 (§12): правильное смещение **+60** (EditorTools), проверка экспортёра по +329 для 32-битных индексов не срабатывает. Остаются: порядок полей `GeometryFragment` (на 301 реальном ресурсе читается без ошибок, но это не доказательство порядка) и `AOgame.pdb`, который не открывается в `llvm-pdbutil`.

## 2. Как игра хранит данные (общая модель, сведённая из всех источников)

### 2.1 Контейнеры

- **`.pak`** — ZIP-совместимый архив. Экспортёр читает его обычным `zipfile`, AODataViewer — через SharpZipLib. Часть записей внутри — ещё один слой zlib (AODataViewer проверяет первые два байта `78 9C`). **СВЕРЕНО** с нашим `docs/formats/pak.md`.
- **`LocPack.rus` / `LocPack.eng`** (клиент 1.1) — тоже ZIP, хотя расширение не `.pak`. Экспортёр выбирает один язык явно и не склеивает.
- **Приоритет наложения паков экспортёр сознательно не угадывает** (`# Patch overlay precedence is deliberately not guessed`). Нам тоже стоит не угадывать, а брать порядок из `DataPacksInfo.bin` (наш `packsinfo.rs`).
- Клиент умеет читать и «рассыпные» файлы из `data/`: `AllodsV4_Developer` проверяет существование файла по `../data/<путь>`. Использовать это знание можно только как факт для «патч-паков» (SPEC блок C), код этого проекта не нужен.

### 2.2 Файл `.bin` внутри пака: что это

Все `.bin` — один поток zlib. Внутри — список блоков `u32 id, u32 size, bytes`:

| Тип ресурса | Что лежит в блоках | Источник |
|---|---|---|
| Texture, UITexture | блок `id` = номер mip-уровня; чтение идёт до `id == 0`, самый маленький уровень первым; большие уровни лежат в соседнем `.hi.bin` | EditorTools `ReadMipmaps`, AOUIEditor, наш `texture-bin.md` — **СВЕРЕНО** |
| Geometry | `0` — вершины, `1` — индексы (16 бит), `2` — скелет, дальше KD-деревья и фрагменты | exporter, blender-import — **СВЕРЕНО**, объясняет «неизвестные u32 0/1/2» из `geometry-bin.md` |
| SkeletalAnimation | блок `0` — данные клипа | exporter |
| ParticleSets, CollisionMesh, terrainDump | блок `0` — данные | exporter |

Где в `.bin` нет описания размеров (ширина, формат), они берутся **из базы ресурсов** (§2.3). Это главная причина, почему без базы приходится угадывать (наш `texheur.rs`, 98 % на клиенте 1.1).

### 2.3 База ресурсов `Bin/pack.bin` (и `Maps_*.bin`)

Одна и та же идея во всех поколениях: **дамп C++-объектов из памяти плюс таблица релокаций указателей**.

Формат V1 (клиенты до 15.0, 32 бита; клиент 1.1.02.0 — сигнатура `5847DB469364493C`), ПРОЧИТАНО в `doc/bin-format.md` EditorTools и в `geometry.py` экспортёра, **СВЕРЕНО**:

| Блок | Содержимое |
|---|---|
| 0 | 8 байт хеша версии (хеш определений структур, не номер релиза) |
| 1 | TxtFiles: id → имя `.txt` для `TextFileRef` (только в главной базе) |
| 2 | Metadata: четыре таблицы с корзинами по Adler-32 имени (mod 65521): DbId→File, список структур, ResId→DbId, DbId→ResId |
| 3 | Data: образ памяти |
| 4 | Fixes: записи по 8 байт, `data` = тип (биты 0–1) + флаг external (бит 2) + адрес/4 (биты 3+); `value` — dbid либо смещение |
| 5, 6 | PakFileRefs и Packs (UTF-16 имена паков), необязательные |

Типы релокаций: `0` DbIdRef (ссылка на корень другого ресурса), `1` Direct (указатель внутри Data, длина лежит следом на +4), `2`/`3` Type/Generic (индекс структуры в списке из Metadata — **так база знает, какой тип лежит по адресу**).

V2 (с 15.0): заголовок — 12 байт без обрамления, нет TxtFiles, в Metadata пять таблиц (добавлена ObjId→DbId), 64-битные поля, записи Fixes по 16 байт, адрес ×8. Это ровно то, что наш `db.rs` уже читает «на уровне каркаса».

**Как определяется тип корневого объекта:** по записи Type/Generic в таблице Fixes. Экспортёр так и делает (`scene.ResourceDatabase.kind`): «database's type tags decide which resource reader to use». Имя ресурса по dbid берётся из Metadata (DbId→File), а имя `.bin` соответствует имени `.xdb` с заменой суффикса (`X.(Geometry).bin` ↔ `X.(Geometry).xdb`).

### 2.4 Схема и раскладки структур

Три независимых описания одних и тех же типов:

1. **EditorTools:** `[StructSize(n)]` + `[FieldOffset(k)]` + `[XdbName]` + `[EnumRef]` на каждое поле. Пять версий. ПРОЧИТАНО.
2. **`AllodsLegacy-server-data/Types/types.xml`:** схема сериализации (имя поля, тип, `ChunkID`, атрибуты `readonly`, `hidden`, `allowDefault`). Это схема для XML/редактора, а не память, смещений в ней нет. ПРОЧИТАНО (фрагмент `client.Scene3D.Geometry`).
3. **PDB-символы:** точные размеры и смещения из компилятора. Лежат в `ao-helper/PDB/Gamer` (AOgame.pdb 78 МБ и др.); экспортёр опирается на PDB клиента 1.1 (`Animation.pdb`, `Widgets.pdb`, `UIState.pdb`), а они, судя по `docs/CLIENTS.md`, есть в «пакете редактора карт» у владельца (144 `.pdb`).

### 2.5 Слой XDB: как ресурсы ссылаются друг на друга

`AllodsLegacy-server-data` показывает реальную форму (ПРОЧИТАНО на примерах):

- Файл `Имя.(Тип).xdb` — XML. Корень = тип (`VisCharacterTemplate`, `IndexedTexture`, `SpellVisScripts` …). Ссылка: `<field href="Файл.(Тип).xdb#xpointer(/Тип)"/>`. Путь с ведущим `/` — от корня `data`, без — относительно файла. Источник `//Characters/...mb` — исходник художника, в игре его нет.
- Цепочка персонажа: `VisCharacterTemplate` → `characterVisObject` (`VisObjectTemplate`, **клиентский тип, в серверных данных отсутствует**) → геометрия, скелет, анимации; плюс `animationProperties`, `defaultDress` (`VisualItem`), `morphSettings`, звуки (`CharacterSoundVariation`: имя анимации → FMOD-проект + имя события).
- `VisualItem`: `dressSlot`, `texturePatches`, `armorShapes` (ветки unisex/male/female; элемент = `armorScene`, `locatorName` вида `Slot_Special01`, `color`, `maskColor`), `hiddenGeosets` (списки `hands_1`, `boots_2`, `hair_11` …). Так одежда выбирает видимые подсетки одной общей модели.
- `IndexedTexture`: `type` (DXT5 …), `width/height/realWidth/realHeight`, `mipsNumber`, `binaryFile` + размер, **`binaryFile2` (`.hi.bin`) + размер**.
- Визуальные скрипты (`SpellVisScripts`, 1642 файла): деревья `VisActionList` с типизированными элементами (`CreatureAnimationAction` со списком анимаций и каналом, FX на кастере/цели, локаторы, `Trail` …).
- Перечень типов в серверных данных: VisualItem 11 572, MobWorld 7689, ItemResource 7560, StaticObject 6385, DBNMesh 4445, Cue 5050, SpellVisScripts 1642 и т. д.

Практический вывод: **сложный объект (модель + анимации + FX + звук) на самом деле граф из десятков ресурсов.** Чтобы экспортировать его «одним набором», нужен граф зависимостей. Экспортёр его строит (`source_index.dependency_graph`, `bundles.*`), мы — нет.

## 3. Аудит инструментов

### 3.1 allods-resource-exporter (Python, MIT) — главный источник

**Что делает** (CLI `allods-export`, 29 команд): `archive-list`, `extract`, `database-list`, `localization`, `mesh`, `texture`, `character`, `animation`, `skeleton`, `collision`, `particles`, `scene`, `terrain`, `location`, `dependencies`, `models`, `appearance`, `creatures`, `effects`, `materials`, `sky`, `items`, `abilities`, `content`, `texts`, `ui`, `ui-images`, `portraits`, `audit-publication`.

**Архитектурные решения, которые стоит перенять** (ПРОЧИТАНО `AGENTS.md`, `archives.py`):
- Все входы явные, исходные файлы только для чтения, вывод только в **новую** папку вне репозитория и вне входов, существующее не перезаписывается (`output_path`).
- Лимиты распаковки на каждом шаге (256 МБ на запись, `inflate` проверяет конец потока и хвост), неизвестные раскладки и флаги — явная ошибка, никаких догадок.
- Отчёт `*.report.json` рядом с каждым экспортом: SHA-256 сжатого и разжатого, размеры, границы, число вырожденных треугольников, список ограничений.
- Статусы пакета: `SOURCE_BUNDLE_OK` / `SOURCE_BUNDLE_PARTIAL` (известные неподдержанные ветки сохраняются в JSON, «частично» не выдаётся за «полностью»).
- Круговая проверка: после записи OBJ файл читается обратно, и отпечаток (SHA-256 от вершин и граней) обязан совпасть.
- Тесты только синтетические, игровых данных в репозитории нет (то же правило, что у нас).

**Как определяются данные и что именно декодируется** (ПРОЧИТАНО; смещения 1.1.02.0):

| Область | Как устроено | Модуль |
|---|---|---|
| База | `Bin.pak` → `Bin/pack.bin` → zlib → блоки 0..4; проверка хеша `5847DB469364493C`; `fixes[адрес] = (тип, цель, external)`; имена из Metadata | `geometry.Database` |
| Ресурсы | при старте сканируются все `*.pak`: `X.(Geometry).bin` → ключ `X.(Geometry).xdb`; то же для `(Texture).bin`; локализованные текстуры берутся из `LocPack.<язык>` | `geometry.Resources` |
| Геометрия | корень: размер вершинного блока +48, индексного +244, скелета +80; массив деклараций вершин +28 (по 92 байта: stride +40, позиция +44, UV0 +28, нормаль +56); массив `modelElements` +180 (по 112 байт); у элемента: id декларации +8, база вершин +12, `skinIndex` +16, имя +20, имя материала +32, диффузная текстура — запись Fixes по +84, «расширение материала» по +80; LOD: массив +96 по 20 байт | `geometry.read_meshes` |
| Вершина | позиция `float3`, UV `float2`, нормаль — 4 байта, XYZ как `c/127.5 − 1` (порядок XYZ, **не** BGRA, как у D3DCOLOR), индексы 16-битные | то же |
| Текстуры | запись `Texture`: тип +32 (0/1/2 = DXT1/3/5), ширина +52, высота +56, число mip +60; декод BC1/2/3 на чистом Python; проверка размера каждого mip | `textures.py` |
| Скелет | блок 2 геометрии: четыре массива (относительное смещение, счёт): узлы по 52 (матрица 3×4 обратной bind-позы = 48 байт, колонки подряд, + `u16` родитель +48), имена по 8, порядок `u16`, локальные преобразования по 48; проверка циклов и сингулярности | `skeleton.py` |
| Клип | заголовок `u16 fps, u16 frames`; массивы: атомы по 20 байт (+4), имена (+12), порядок (+20), материальные атомы (+28), их имена (+36) | `animation.py` |
| Атом преобразования | `flags u16` + `varying u16`; 7 каналов: 4 скаляра (x, y, z позиции и масштаб) и 3 угла. Бит флага = канал постоянный. Переменный скаляр: пара `(min, step)` в постоянных данных + `u16`-код кадра, значение = `min + step·код`. Угол: `u16 × 2π / 65536`. Проверка `varying == 7 − popcount(flags)` | `animation.SkeletalClip.sample` |
| Материальный атом | флаги: 1 — прозрачность (байт), 2 — сдвиг U (`u16`, с заворачиванием), 4 — сдвиг V; прозрачность = «сколько убрано» (используется `1 − t`) | `sample_material` |
| Частицы | `ParticleSets`: эмиттеры по 48 байт, у частицы каналы позиции (`3H`), масштаба (`2H`), поворота (`H`), цвета (`4B`), спрайта (`B`); времена ключей `u8` или `u16` в зависимости от жизни; это **кэш дорожек, не симуляция** | `particles.py` |
| Коллизия | корень `u32` = размер−4; массив граней по 24 байта: плоскость `4f` + массив плоскостей рёбер; вершины восстанавливаются пересечением трёх плоскостей, проверяются выпуклость, единичность нормалей, ориентация обхода | `collision.py` |
| Террейн | `terrainDump` (`TerrainSetFixed` LOD0): материалы по 9 байт, патчи по 32, подпатчи по 40; вершины 8 или 12 байт на вершину (упакованная нормаль + индекс сетки + высота + необязательный счётчик); две поверхности (верх/низ); отсечение по знаку `normal.z·(h1−h2)` (повторяет шейдер) | `terrain.py`, `terrain_topology.py` |
| Локализация | `Bin/pack.loc`: три блока (имена→слот, таблица (длина, смещение), строки UTF-16) | `localization.py` |

**Выходные форматы:** OBJ + MTL (без потерь, Z вверх), PNG/DDS, **GLB** со скелетом, скином, клипами и текстурами (преобразование XYZ→`(X, Z, −Y)`, V переворачивается ровно один раз), террейн-GLB с необязательной запечённой текстурой, `objects.glb` с инстансами, JSON-отчёты, `creature_combat.bin` + `_assets.zip`.

**Что экспортёр не умеет** (его собственные границы): нет записи, нет 3.0 и новее, нет `TrailComponent`, нет шейдеров, нет воспроизведения контроллеров и состояний боя, нет звука, UI-скриптов (Lua) тоже нет. Документы `docs/` (api, compatibility, pipelines, terrain, validation, publication, references) в архиве есть и совпадают с репозиторием `github.com/enoly/allods-resource-exporter` (проверено `diff`); в `terrain.md` и `validation.md` автор записал результаты прогона на своём корпусе 1.1.02.0 (карта Kania_AL1: 13 тайлов террейна, 964 размещения объектов, 60 моделей, 1553 клипа существ, 74 ресурса частиц, импорт в Blender 5.2.3). Это его собственные заявления, мы их не перепроверяли.

**Что и как портировать — см. §6.**

### 3.2 AllodsOnlineEditorTools (C#, MIT)

**Что делает:** `pack unpack/ls/info` (база → `jdb` или `xdb`, из папки или из пака), `texture bin export` (в DDS/PNG), `utils compress/decompress`, `info versions`, `--as <версия>` (приведение к структурам другой версии), `structs generate` (в открытой сборке выключена).

**Устройство** (ПРОЧИТАНО):
- `GameVersion.cs`: таблица из девяти хешей → версия; у каждой версии свой namespace структур (`V1_1_02_0`, `V3_0_00_89`, `V4_0_02_43`, `V7_0_00_76`, `V14_0_01_71`), тип ссылок на файлы (`FileRef`, `FileRef2`, `PakFileRef`), формат базы (V1/V2). Хеш 17.0.01.55 (12 байт) распознан, структур нет.
- `BinaryStructReader` — рефлексивный читатель по `[FieldOffset]`: примитивы, строки (указатель из Fixes + длина +4; UTF-8, «широкие» — UTF-16), массивы, `ResourcePointer` (DbIdRef), `NullablePointer`, `FileRef`, `TextFileRef`, векторы, кватернионы, AABB. Абстрактные типы без записи Type не читаются.
- Сериализаторы `Jdb` и `Xdb` (XML, имена полей из `[XdbName]`, свой формат float), у каждого читатель и писатель, много тестов (JdbRead 16, JdbWrite 28, XdbRead 31, StructCaster 15 и др.; проверка раскладки `StructLayoutValidation`).
- Кросс-версионный `--as`: поля сопоставляются по имени, энумы переотображаются по имени записи.
- Текстуры: энум `TextureType` (DXT1, DXT3, DXT5, RGBA, L8, D24, D16, C565, C4444, RG16, R32F, RGBA16); DDS-заголовок пишется с FourCC = имя типа. **Замечание:** для не-DXT типов FourCC `RGBA`/`L8`/… не является валидным DDS-описанием, такие файлы большинство программ не откроют; нам нужны маски пикселя или заголовок DX10.
- Энум `VertexElementType` (FLOAT1..4, SHORT2, SHORT4, COLOR4, UBYTE4, USHORT2, USHORT4, HALF4, UNUSED) — **СВЕРЕНО** с blender-import и с нашим чтением (веса COLOR4, индексы UBYTE4).

**Чего нет:** раскладок для 17/18, импорта DDS, записи `.bin`/`.pak`, работы с геометрией и анимацией (только база и текстуры).

### 3.3 AllodsOnlineDatabaseUnpacker (C#, лицензия не указана)

Загружает **родные DLL игры** (`Main`, `libdb`) через P/Invoke и читает объекты из памяти запущенного кода (`InitEditorDataSystem`, `GetObject` по `ThisCall`). Только Windows x86, одна версия. Подход исключён (мы не запускаем чужой нативный код; уже решено в `TOOLS-STUDY.md`). Полезно только как **справочник значений**: энумы `Animation` (579 имён анимаций), `DressSlot` (30), `ModelMorphControl` (15), `TextureElementType`, `VertexElementType`, `BlendEffect`, `WidgetSizing/Align`, `CollisionVolume`, `CreatureKind`. Имена анимаций нужны нам для подписей клипов (в клипах хранятся числовые id). Все три копии (`dev`, `master`, `master_1`) по содержимому идентичны, `dev` отличается от `master` нулём файлов.

### 3.4 blender-import (Python, лицензия не указана)

Читает `.xdb` (XML, в архиве есть образцы) и `.bin` геометрии: блоки по `localId`, `modelElements` с LOD-диапазонами, декларации вершин, кости (52 байта + имена + порядок + локальные матрицы); создаёт меши и UV, **без** скелета, анимаций, материалов (разбор материала закомментирован). Протестирован только на Blender 2.90, использует `distutils` (удалён в Python 3.12). Как код непригоден; как факт — единственное, что есть: схема XML материала (`BlendEffect` 0..4 = ADD, ALPHA, ALPHA_ADD, COLOR, COLOR_ADD; поля `scrollAlpha`, `scrollRGB`, `uTranslateSpeed`, `vTranslateSpeed`, `transparencyTexture`, `useFog`, `visible`).

### 3.5 AODataViewer (C#, NeoAxis, лицензии нет)

Просмотрщик на движке NeoAxis (.NET 4.7). Читает паки из `data` и `data_warp`, `.loc` (раскладка 1), показывает текст, геометрию «без скелета» и текстуры. Угадывает ширину вершины (24/28/32/36) по признакам в байтах, даёт ручной редактор формата вершины (размер, позиция, UV, «неизвестное»), экспортирует модель только в FBX (с поворотом и масштабом). Окна: пак-дерево, поиск по тексту, информация о версии. Знаний о форматах сверх уже имеющихся у нас нет; полезны идеи интерфейса (ручная подгонка формата — у нас есть выбор размера по Ctrl+клик). 109 бинарных DLL движка — не наши и не для репозитория.

### 3.6 AOUIEditor (C#, MIT) — для слоя интерфейса и аддонов

ПРОЧИТАНО README, `UITexture.cs`, `DxtDecoder.cs`. Факты:
- Аддон = папка с `.xdb` (UTF-8 без BOM), `.txt` (UTF-16LE), `.lua` (Windows-1251). Ссылки `href` в редакторе относительны к папке аддона; ссылка на внутриигровой ресурс начинается с `/`.
- Виджеты наследуют **прототипы**; пустое свойство берётся из прототипа, затем из прототипа прототипа, затем по умолчанию. Именованные переменные прототипа редактор не поддерживает.
- Слои: `WidgetLayerSimpleTexture`, `WidgetLayerTiledTexture` (поля Left/Middle/Right, X/Y; правила разработчика игры: Middle — 0 или 2^N, N ≥ 5, и др.), `WidgetLayerAnimatedTexture`. Режимы смешивания UI: ALPHABLND, ADD, HIGHLIGHT и др.
- `UITexture`: `binaryFile`, `width/height` (степень двойки), `realWidth/realHeight`, `type`; `.bin` — «zlib с добавленными в начало 78 9C», первые 8 байт блока — информация о mip.
- Типы, которые редактор **не** перезаписывает: UITextureElement, UISingleTexture, UITexture, DecalTemplate, FMODProject, VisObjectTemplate (создаются специальными программами).
- В архиве лежат реальные ресурсы игры (`.bin` UI-текстур) — в наш репозиторий их копировать нельзя (правило «игровых данных нет»).

### 3.7 AllodsV4_Developer (C++) — не портируем

Внедряемая DLL: заглушка `GetSystemTime` (дата 24.05.2013), перехват `CreateFile`, модуль `Replacer` (регулярные замены в `.xdb` на лету), `Client::patchVersion` (правка кода клиента по фиксированному адресу), модули `Protector`, `Crasher`. Это вмешательство в процесс игры и обход защиты. В план не входит. Единственное, что мы фиксируем как наблюдение: клиент ищет «рассыпные» файлы по `data/` (см. §2.1).

### 3.8 Репозитории `ao-helper-rv168362` и `AllodsLegacy-server-data`

- `ao-helper`: PDB (`Gamer/AOgame.pdb` 78 МБ, `UIConverterAPI.pdb`, `Launcher.pdb` …) — источник точных раскладок. `LocKit` (лаунчер/локализации), `Server/*.Server.pak` (серверные паки карт), `Unprotected/` (незащищённые сборки), `ObfuscationTools`, `PatchTools`. Последние три группы мы **не используем**: они связаны с защитой и модификацией клиента.
- `AllodsLegacy-server-data`: полное XML-дерево ресурсов сервера 4.0.4.42 и `Types/types.xml`. Ценность: реальные имена ресурсов и форма `.xdb` (§2.5), схема типов, тестовые образцы XML-парсера **без** чужих игровых бинарников.
- Объёмы: ao-helper — 1,3 ГБ, server-data — 1,9 ГБ. Клонировать полностью в CI нельзя; для разработки нужны выборки (список в §8).

## 5. Принципы портирования

1. **Порт из MIT — только с записью в `NOTICE` в том же коммите.** Из остальных — только факты своими словами, через `docs/formats/*.md` с пометкой источника и статуса (`claimed`/`confirmed`).
2. **Читаем данные, а не исполняем чужой код.** Подход «загрузить DLL игры» (Unpacker) исключён.
3. **Раскладки — данные, а не код.** Вместо тысяч сгенерированных структур — таблицы раскладок (TOML/JSON, по одному файлу на версию клиента), которые общий читатель применяет к образу памяти. Преимущества: добавить версию = добавить файл; таблицы проверяются автоматически (размер структуры, пересечения полей, выход за образ); из них генерируются документация, шаблоны ImHex и тесты. Файлы таблиц не содержат игровых данных.
4. **Строгость как у экспортёра:** неизвестная раскладка или флаг — явная ошибка; частичный результат помечается `PARTIAL` с перечнем причин; к каждому экспорту прилагается отчёт с SHA-256.
5. **Каждый формат — три уровня:** (a) чтение сырых байтов, (b) декодирование в нашу модель, (c) экспорт. Проверка уровня (a) не должна зависеть от (c).
6. **Версия клиента определяется по хешу базы** (таблица EditorTools из девяти хешей + наши 18.0), а не по имени папки.
7. **Проверка на реальных образцах — отдельный шаг:** «синтетический тест прошёл» не равно «verified» (правило из `CONTRIBUTING.md`).

### 6.6 Экспорт в общепринятые форматы

**Модели**
- OBJ + MTL — уже есть; добавить круговую проверку отпечатка (идея экспортёра).
- **GLB:** скелет, скин, **все клипы**, текстуры, подсетки как отдельные примитивы, `extras` с исходными индексами и именами; преобразование Z-up → Y-up `(x, z, −y)`, V переворачивать ровно один раз, строки PNG не трогать; матрицы с отражением или сдвигом — отказ, а не молчаливая потеря.
- Материальные дорожки (UV-скролл, прозрачность): стандартный glTF их не умеет, варианты — расширение `KHR_animation_pointer` (если принимается целевыми программами) либо запись в `extras` + аддон Blender. Решение за владельцем.
- LOD: отдельные узлы `*_lod1`… (как blender-import), либо одно LOD по выбору.
- Коллизия: отдельный GLB или узлы-каркасы.
- FBX (ожидание из AODataViewer): через Blender после GLB; собственный FBX-писатель не планируем.

**Текстуры:** PNG (RGBA8), DDS, TGA; склейка `.hi.bin`; нарезка атласов UI по `UITextureElement`; запись `realWidth × realHeight` как опция обрезки (уже есть `--crop`).

**Тексты:** `.loc` → TSV/CSV/JSON/XML/HTML (есть); добавить разрешение `TextFileRef` в ключи по базе; PO/XLIFF — по желанию.

**Звуки:** WAV, MP3 (есть); OGG как проход Vorbis без перекодирования — отдельная задача (в FSB5 заголовки Vorbis восстанавливаются по таблице настроек, у нас она есть); связь «объект → события» (`adv db sound`, `CharacterSoundVariation`).

**«Комплекс модели»: модель + анимации + FX + звук как один набор.** Предлагаю формат **bundle**: папка

```
Elf_female/
  manifest.json          схема версии, граф зависимостей, статусы OK/PARTIAL, хеши
  model.glb              меши, скелет, скин, текстуры
  clips/<имя>.glb|.json  клипы (или встроены в model.glb)
  materials.json         общие материалы, UV-дорожки, режимы смешивания
  attachments.json       локаторы Slot_*, наборы одежды, скрытые подсетки
  fx/<имя>.json + sprites/*.png   кэш частиц, атласы с раздельными UV для RGB и альфы
  collision.glb
  sounds/<проект>/<событие>.wav + sounds.json
  states.json            CreatureVisState, визуальные действия (деревья VisActionList)
```

Составляется по графу A-6; неподдержанные ветки (например, `TrailComponent`) остаются в `manifest.json` как `PARTIAL` с причиной, как делает экспортёр. **Импорт в Blender:** собственный аддон под актуальный Blender (4.x), читает `manifest.json`: коллекции, арматура, действия (клипы), пустые объекты-локаторы, динамики-звуки; без `distutils` и без привязки к 2.90 (то, на чём споткнулся blender-import).

**Карты и окружение:** `terrain.glb` с необязательной запечённой текстурой (экспортёр: расщепление на верхний и нижний слои, отсечение по знаку `normal.z·(h1−h2)`), `objects.glb` с инстансами, `scene.json`, `MinimapTexture` → PNG, вид сверху → PNG/SVG (M13). Небо и освещение (`sky`, `ZoneLights`) — низкий приоритет.

### 6.8 Клиент 18.0 (x64): вывод раскладок

Это главный риск проекта: готовых источников нет. Предлагаемый порядок работ:

1. **Собственный читатель PDB** (формат MSF 7.00, поток TPI). `llvm-pdbutil` из LLVM открывает `UIConverterAPI.pdb` и `Launcher.pdb`, но на `AOgame.pdb` выдаёт «Too many directory blocks» (размер блока 1024 байта и крупный каталог потоков). Нужен либо крейт `pdb` (проверить лицензию и политику), либо собственный разбор каталога потоков — это небольшая задача. Выход — таблицы раскладок типов клиента 1.1 (`NDb::Geometry` и т. д.) для **сверки** смещений EditorTools и экспортёра.
2. **Схема 18.0:** для текущего клиента PDB нет. Используем схему типов (`types.xml` содержит поля и `ChunkID`, но не смещения) и **вычисляем раскладку** по правилам MSVC x64 (выравнивание, размеры указателей 8 байт). Проверка: размеры структур из базы (расстояния между объектами в образе) и контрольные поля, уже проверенные у нас (`Texture`: тип, размеры, mip).
3. **Контрольные ресурсы** для 18.0: один `Texture`, один `Geometry`, один `SkeletalAnimation`, один `Material` — чтобы подтвердить вычисленные раскладки на реальных объектах (в `docs/GAPS.md` уже просили образцы).
4. До готовности 18.0 сначала выпускаем поддержку 1.1 и 7.0, где раскладки уже известны; пользователь 18.0 получает прежние функции без регресса.

## 10. Решения владельца (2026-11-26) и вопросы

Решено:
- Область: версии клиента **до перехода на 64 бита**, наращивать поддержку плавно, не ломая работающее. Клиент 18.0 отложен.
- Запись базы ресурсов (W-6) — **цель проекта** (этап P9). Следствие: таблицы раскладок проектируем сразу «читать и писать», а круговой тест `read → write → побайтное сравнение` обязателен.
- Материальные дорожки в glTF: делаем **оба варианта с переключателем** (`extras` + аддон Blender, и расширение `KHR_animation_pointer`); по умолчанию `extras`, потому что он работает везде.
- FBX: в `ROADMAP` как необязательный пункт «после bundle и аддона Blender» (рекомендация Claude); сейчас не реализуется.
