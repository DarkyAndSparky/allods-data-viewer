# Форматы: план чтения и проверок

Подробные описания форматов со статусом проверки, алгоритмами чтения и планом тестов. Источник правды по самим форматам: `docs/formats/*.md`; если этот файл и они расходятся, прав `docs/formats/*.md`.

## 1. Статусы и как им верить

Каждое утверждение о формате имеет статус. Это главное правило проекта: неизвестное остаётся неизвестным.

| Статус | Значение |
| --- | --- |
| `verified` | проверено на реальных файлах, каждый элемент разобран, остатка нет |
| `draft` | описание из чужого MIT-проекта или наблюдение без полной проверки |
| `unknown` | ничего достоверного нет, нужны образцы |

## 3. Определение формата (`detect`)

Порядок проверки, от дешёвого к дорогому. Читаются только первые 64 байта, имя файла вторично.

| Признак | Результат | Статус признака |
| --- | --- | --- |
| `50 4B 03 04` или `50 4B 05 06` в начале | ZIP, то есть `.pak` | verified |
| `78` и одно из `01`, `5E`, `9C`, `DA` | слой zlib: распаковать, повторить определение | verified |
| после распаковки `00 00 00 00`, затем 4 байта | `.loc` раскладки 1 | verified |
| после распаковки `62 0F 2E 16` | `.loc` раскладки 2 | verified как признак |
| `4F 67 67 53` (`OggS`) | Ogg, то есть `.ogv` | по общим знаниям, проверить |
| `46 53 42` (`FSB`) и цифра версии | FMOD `.fsb` | по общим знаниям, проверить |
| `44 44 53 20` (`DDS `) | DDS-текстура | по общим знаниям, проверить |
| `00 01 00 00`, `74 72 75 65` или `4F 54 54 4F` | шрифт TrueType или OpenType | по общим знаниям, проверить |

Если признаки не сработали, вид решается по расширению и по контексту (запись базы ресурсов называет тип). Для `.bin` без базы текстуру от базы данных не отличить: нужен контекст.

## 4. `.pak`

**Статус: verified (контейнер).** Раскладка описана в `docs/formats/pak.md`.

- Файл это обычный ZIP. Читаем по центральному каталогу, не по сигнатурам записей.
- Пути с `/`. Каталоги (имя оканчивается на `/`) пропускаем.
- Методы: 0 (stored) и 8 (deflate). Любой другой метод это ошибка `Unsupported`.
- CRC32 проверяется при чтении записи целиком. При чтении потоком проверка делается на последнем блоке.
- Игра держит паки в `data/Packs/` (в некоторых версиях ещё `data_warp/Packs/`); все паки образуют одну виртуальную файловую систему.

Алгоритм открытия записи (предложение):

1. Найти запись по пути (без учёта регистра, ASCII; см. `docs/CORE-DESIGN.md`, раздел 5).
2. Прочитать данные с учётом метода и проверить, что размер не превышает лимит.
3. Если режим `Decoded` и первые два байта похожи на zlib, попытаться распаковать. При ошибке отдать исходные данные и записать предупреждение.
4. Если режим `Raw`, отдать данные после слоя ZIP как есть.

Лимиты (предложение, числа обсудить): число записей в паке до 10 000 000; распакованный размер записи до 2 ГиБ; общий размер слоя zlib после распаковки до 1 ГиБ; отношение распакованного к сжатому до 2000 : 1 для записей крупнее 1 МиБ (защита от архивов-бомб). Нарушение даёт ошибку `Limit`. Подробнее: `docs/SECURITY-AND-QUALITY.md`.

Тесты: синтетический ZIP, собранный в коде (stored, deflate, пустая запись, запись из нескольких блоков); обрезанный каталог; неверный CRC; путь с `..`; путь с абсолютным префиксом; дубль пути; запись с расширенным (ZIP64) размером.

Открытые вопросы: Q-03 (дубли путей между паками), шифрование.

## 5. `.loc`, раскладка 1 (32 бита)

**Статус: verified.** Все числа little endian. Положения отсчитываются от конца заголовка (прибавьте 16, чтобы получить смещение в файле).

| Смещение | Тип | Смысл |
| --- | --- | --- |
| 0 | u32 | всегда 0 |
| 4 | u32 | `sizes_pos`, положение таблицы размеров |
| 8 | u32 | всегда 8 |
| 12 | u32 | `count`, число элементов |

Дальше:

1. Таблица элементов сразу после заголовка: `count` записей по 12 байт: `pos` (u32), `str_size` (u32), `id` (u32); `id` равен номеру записи.
2. Ключ: `str_size` байт UTF-8 по адресу записи плюс `pos` (отсчёт от начала самой 12-байтной записи). Последний байт нулевой, значит ключ занимает `str_size - 1` байт.
3. Таблица размеров по `sizes_pos`: `count` записей по 8 байт: `length` (u32, в единицах UTF-16) и `pos` (u32).
4. Текст элемента `id`: `length` единиц UTF-16 (то есть `2 * length` байт) по адресу `конец_таблицы_размеров + 8 + pos`, затем нулевой терминатор из двух байт; тексты выровнены по 4 байта.

Алгоритм чтения с проверками (предложение):

```
read_loc_v1(data):
    require len >= 16; word0 == 0; word2 == 8
    count = u32(12); require count <= MAX_ITEMS
    require 16 + count*12 <= len                       // таблица элементов
    require 16 + sizes_pos + count*8 <= len            // таблица размеров
    for each record i in 0..count:
        key_at = 16 + 12*i + rec.pos                   // проверить диапазон и NUL в конце
        key = utf8(data[key_at .. key_at + str_size - 1])   // ошибка Format при невалидном UTF-8
        text_at = 16 + sizes_pos + count*8 + 8 + size_rec.pos
        require text_at + 2*length + 2 <= len
        text = utf16le(data[text_at .. text_at + 2*length])  // непарные суррогаты: заменить и записать предупреждение
```

Применяются checked-операции для всех сложений и умножений. Невалидные суррогаты не должны ронять разбор.

Экспорт: CSV (ключ, текст) в UTF-8 с BOM по выбору, JSON (массив объектов), построчный TSV. Разметка `<span>`, `<r name="..."/>` сохраняется как есть.

Тесты: сборщик в коде строит `.loc` из списка пар; проверки на пустой файл, `count = 0`, обрезанную таблицу, ключ без NUL, текст за концом файла, `str_size = 0`, невалидный UTF-8 в ключе, непарный суррогат. При `ADV_SAMPLES`: три реальных файла, у каждого последний текст заканчивается ровно в конце файла.

## 6. `.loc`, раскладка 2 (64 бита)

**Статус: draft.** Файлы `pack.rus.loc` и `pack.eng_eu.loc` (около 45 МБ после распаковки) устроены параллельно: одинаковая структура, русский и английский текст.

Начало данных состоит из 64-битных слов: `0x162E0F62`, `566294`, затем пары (n, смещение): (9, 16), (15, 40), (6, 72), (6, 72) и далее. Первое слово это магия. Второе слово вероятно число элементов (в обоих файлах совпадает). Смысл пар не расшифрован.

План расшифровки (по порядку, без угадывания):

1. Взять оба файла, сравнить их: что совпадает побайтно (структура), что отличается (тексты).
2. Проверить гипотезу «пара = (длина, позиция)» на первых десятках пар: попадает ли позиция на осмысленные данные.
3. Найти, где лежат ключи (ищем строки вида `Characters/.../Name.txt`), где тексты UTF-16.
4. Записать раскладку в `docs/formats/loc.md`, подтвердить на обоих файлах (каждый элемент разобран, остатка нет), только после этого статус `verified`.

Что потребуется от вас: образцы с нескольких версий (см. `docs/SAMPLES_REQUEST.md`), особенно версии, где раскладка 1 и раскладка 2 соседствуют.

## 7. Текстуры `.bin`

**Статус: draft.** Описание из MIT-проекта; нашими файлами не проверено.

- Файл это поток zlib. После распаковки идёт последовательность кусков: `id` (s32), `size` (s32), затем `size` байт пикселей. Чтение заканчивается после куска с `id` равным 0.
- Куски лежат от **самого маленького mip-уровня** к большому; для результата их нужно развернуть.
- Данные блочно сжаты (DXT). Ширина, высота, число mip и тип сжатия **не лежат в файле**: они берутся из описания текстуры в базе ресурсов. Тип сжатия становится FourCC в заголовке DDS.
- Чтобы получить `.dds`: записать заголовок DDS (FourCC, размеры) и затем mip-уровни от большого к малому.
- Чтобы получить PNG: распаковать DXT1/DXT3/DXT5 в RGBA самим (модуль `codec/dxt.rs`), закодировать через крейт `png`.

Пока базы ресурсов нет (веха M6), в CLI будет режим с явными параметрами: `adv tex extract <файл> --width W --height H --format dxt1|dxt3|dxt5 --mips N`. Позже размеры берутся из базы автоматически.

Проверки: сумма размеров кусков должна совпасть с размером, который даёт формула для DXT (блоки 4 на 4: DXT1 8 байт, DXT3/DXT5 16 байт на блок); размеры текстуры не больше 16384 (предложение).

Тесты: синтетическая текстура 8 на 8 для каждого типа DXT; обрезанный поток; лишний кусок после `id = 0`; несовпадение размеров.

Открытые вопросы: какие типы сжатия реально встречаются (DXT1/3/5, несжатые, другие), есть ли у текстур кубические карты и массивы.

## 8. Базы ресурсов `.bin` (V1 и V2)

**Статус: draft.** Это самый сложный формат проекта: в нём лежит **сырой образ памяти** C++-объектов игры и таблица для исправления указателей.

| Кусок | Смысл |
| --- | --- |
| Header | 8-байтный хеш версии, определяет набор описаний структур |
| TxtFiles | идентификаторы ссылок на тексты (старые клиенты) |
| Metadata | таблицы по корзинам: id в имя файла, имена структур, идентификаторы ресурсов |
| Data | образ памяти |
| Fixes | исправления указателей (id базы, прямой указатель, метка типа) |
| PakFileRefs | необязательно, смещения ссылок на паки |
| Packs | необязательно, имена используемых `.pak` (UTF-16) |

Клиенты 15.0 и новее (V2): вместо куска Header голый 12-байтный буфер версии, нет куска TxtFiles, добавлена таблица идентификаторов, поля 64-битные (в том числе x86 и x64 образы).

Образ памяти разбирается только с точными описаниями структур клиента, поэтому нужны таблицы по версиям. Это основная причина портировать работу MIT-проекта (с записью в `NOTICE`), а не писать с нуля.

План, без обещаний:

1. M6a: читаем контейнер (куски, список Packs, таблица имён Metadata). Это даёт полезный результат без структур: список ресурсов с именами и ссылками на паки.
2. M6b: определяем версию по хешу и спрашиваем таблицу структур. Версия без таблицы получает честную ошибку `Unsupported` с хешем.
3. M6c: JSON/XML экспорт объектов для поддерживаемых версий.

Тесты: синтетическая база из двух кусков; неизвестный хеш версии; Fixes с указателем за пределами Data; цикл в ссылках.

## 9. Звук и видео

**Звук `.bsb`.** Поток zlib. После распаковки первые 4 байта отбрасываются, остаток это обычный `.fsb`. Статус `draft`: основан на скриптах стороннего набора.

**Звук `.fsb`.** FMOD sample bank. Версия формата и кодек неизвестны (предположение: потоки Vorbis, но подтвердить нужно по образцу). После получения образца: описать заголовок, список потоков (имя, частота, каналы, число семплов, смещение), способ вырезать поток, декодировать. Для воспроизведения и конвертации в WAV нужен декодер Vorbis; выбор: `symphonia` 0.6.1 (MPL-2.0, вышел в 2026 году). MP3 только через внешний `lame` или `ffmpeg`, встраивать LAME не будем (LGPL).

**Видео `.ogv`.** По вашему уточнению видео у нас Ogg, и мы работаем с ним как с Ogg. Файлы лежат в `Video.pak` без сжатия. Кодеки внутри (предположительно Theora и Vorbis) подтвердить по одному образцу. План: прочитать заголовки Ogg и показать сведения (длительность, размер кадра, кодеки), воспроизводить в приложении средствами webview; конвертацию в другие форматы делать внешним `ffmpeg`, если он найден. Слово «импорт» из первого плана снято: отдельной задачи нет.

## 10. Модели и материалы

**Статус: unknown.** Формат неизвестен. Не выдумываем. Работа начинается с образцов: комплект из модели, её материала и текстуры одного предмета (см. `docs/SAMPLES_REQUEST.md`, пункт 7). Что нужно будет выяснить: заголовок, вершины и индексы, нормали, UV, скелет и веса, анимации, связь с материалом и текстурой, система координат и масштаб. Результат: glTF 2.0 (`.glb`) и предпросмотр в Three.js. До образцов вехи M7 и M8 не начинаются.
