# Спецификация: доработка по аудиту и конвейер модов

Проект: Allods Data Viewer 0.1.44 (`adv`, `adv-core`, `adv-session`, desktop на Tauri 2).
Тип документа: рабочая спецификация (русский, как `GAPS.md` и `ROADMAP-DETAILED.md`). Имена API, команд и кодов ошибок английские. Если файл будет лежать в `docs/`, CLAUDE.md требует английского языка для документов: тогда перевести перед коммитом.
Предлагаемое место: `docs/SPEC-audit-and-modding.md`.

## 0. Как читать и что проверено

Метки подтверждения взяты из `docs/engineering/WORKFLOW.md`:

- **VERIFIED**: файл или код прочитан мной и вывод следует из текста.
- **NOT VERIFIED**: по рассуждению, на реальных данных или сборке не проверялось.

- Бинарные утилиты `loc.extracter.exe`, `loc.compiler.exe`, `game.ver.info.exe`, `game.ver.truncator.exe` (32-бит, 2009 год, UPX) не запускались и не распаковывались. О их поведении известно только по названиям.
- Проект `AllodsV4 Developer` (DLL, внедряемая в процесс клиента) в спецификацию не входит и использоваться не должен.

## 1. Цели и не-цели

**Цели**

1. Убрать найденные в аудите риски устойчивости и безопасности, не ломая слои (`core` не знает про UI, ни `unsafe`).
2. Перенести в документацию форматов факты из справочных проектов, которые закрывают пункты «Not known».
3. Сделать конвейер для модов: массовая распаковка с манифестом, воспроизводимая упаковка в новый `.pak`, запись `.loc` из таблицы, круговая проверка.

**Не-цели (явно)**

- Изменение баз ресурсов `.bin` (слепок памяти с таблицей релокаций): пока образ не декодирован, запись невозможна (раздел 6.9).
- Упаковка звука (FSB, `.bsb`): нужен кодировщик, M10 её исключает.
- Любое взаимодействие с процессом клиента, обход защиты, правка запущенной игры.
- Распространение игровых данных: в репозиторий они не попадают (правило из CLAUDE.md, проверяет `scripts/check-repo.mjs`).

## 3. Блок A. Надёжность и безопасность

### A-01. Кеш открытых паков

**Проблема (VERIFIED, чтение `crates/session/src/lib.rs`).** `Session::with_pak` держит общий `Mutex<HashMap<PathBuf, OpenPak>>` на всё время выполнения замыкания, то есть на чтение и распаковку. Следствия: команды сериализуются (долгий `search_text` блокирует превью); паника внутри замыкания отравляет замок, и все следующие вызовы возвращают `internal lock poisoned`; кеш не ограничен, каждый `OpenPak` держит открытый файл до закрытия сессии, а на Windows это блокирует обновление клиента.

**Требования**

1. Структура кеша: `Mutex<Cache>`, где `Cache` хранит `HashMap<PathBuf, Arc<Mutex<OpenPak>>>` и порядок использования. Общий замок держится только на поиск или вставку записи, затем снимается. Работа идёт под замком конкретного пака.
2. Вытеснение LRU с лимитом открытых паков (по умолчанию 16, настраивается в `Session::open_with`). При вытеснении пак закрывается (`Drop` освобождает дескриптор).
3. Обход всего дерева (`census`, `find_kind`, `search`, `search_text`) открывает пак временно: если записи нет в кеше, пак открывается, обрабатывается и не вставляется в кеш (режим `no_retain`), чтобы обход не вытеснял рабочий набор.
4. Отравление замка не должно быть необратимым: использовать `lock().unwrap_or_else(PoisonError::into_inner)` и пересоздавать запись, если её состояние нельзя считать целым (флаг `poisoned` внутри `OpenPak`). Паника всё равно логируется как ошибка с кодом `failed`.
5. Публичный API `Session` не меняется (внутреннее изменение).

**Критерии приёмки**

- Тест: два потока читают разные паки, один из них «долгий» (замыкание с `park`), второй завершается, не дожидаясь первого.
- Тест: паника в замыкании над паком A не мешает чтению пака B и повторному чтению A после пересоздания.
- Тест: после обхода `census` по набору из 40 синтетических паков число открытых дескрипторов не превышает лимит (проверка через счётчик в тестовом `OpenPak`-фабрике, а не через ОС).
- `cargo clippy --workspace --all-targets -- -D warnings` без новых замечаний.

**Риски.** Вложенные захваты (замок пака под общим замком) ведут к взаимной блокировке: порядок захвата фиксируется «общий, затем пак», общий всегда снимается до работы.

### A-02. Отмена долгих операций и отчёт о пропущенных

**Проблема (VERIFIED).** `search`, `search_text`, `census`, `find_kind` выполняются в `spawn_blocking` без отмены. Новый запрос не прерывает старый. Ошибки глотаются: `let _ = self.search_dir(...)` и `let Ok(data) = self.read(path) else { return true }`. Пользователь не узнает, что часть паков не прочитана.

**Требования**

1. Тип `Cancel` (обёртка над `Arc<AtomicBool>` из `std`, новая зависимость не нужна). Методы `search`, `search_text`, `census`, `find_kind`, `walk` принимают `&Cancel` и проверяют его на каждой итерации обхода и между файлами внутри `search_text`.
2. Возврат `Err(SessionError::Cancelled)` при отмене. В `commands.rs` код `cancelled` в `AppError`; UI не показывает его как ошибку.
3. Команда `cancel_operation(kind)` и счётчик поколения: новый `search`/`search_text` отменяет предыдущий того же вида автоматически.
4. Отчёт: результаты `search`/`search_text`/`census` содержат поле `skipped: Vec<Skipped>` (путь, причина: `unreadable`, `damaged_pak`, `too_large`, `limit`) и `skipped_total: usize`. Список ограничен (первые 100), счётчик полный.
5. UI показывает «пропущено N» со ссылкой на подробности. Все новые строки добавляются в `web/src/i18n.ts` на русском и английском (требование проекта; `invariants.test.ts` ловит пропуски).

**Критерии приёмки**

- Тест сессии: отмена посреди обхода из 1000 синтетических записей завершается за ограниченное число шагов (счётчик посещённых путей меньше полного).
- Тест: повреждённый пак в середине дерева даёт `skipped_total == 1`, остальные результаты находятся.
- Веб-тест: быстрая смена запроса показывает результаты только последнего.
- Эталон: обход не сломан при `limit == 0` и при пустом запросе (текущие тесты остаются).

**Необязательно (P2).** Индекс текстового поиска по `.loc` (id, ключ, нормализованный текст) в памяти на время сессии с инкрементальным построением. Включать только после измерения, не заранее.

### A-03. `save_as`: диалог на стороне Rust и атомарная запись

**Проблема (VERIFIED).** `commands.rs::save_as` принимает `dest: String` от UI и проверяет только `is_absolute()`. В `GAPS.md` (G-13) сказано «запись только по пути из диалога», но код этого не обеспечивает. Запись `std::fs::write` неатомарна и всегда перезаписывает.

**Требования**

1. Новая схема: UI вызывает `save_as(path, format, texture_index, index)` без `dest`. Rust-команда открывает диалог сохранения через `tauri-plugin-dialog` (уже подключён), получает путь и пишет сам. Права окна `dialog:allow-save` остаются нужны только для самого вызова; прямой доступ окна к файловой системе по-прежнему запрещён.
2. Для пакетного экспорта (C-01) путь выбирается один раз (папка) и хранится в состоянии на стороне Rust до завершения операции. UI не может подставить другой.
3. Запись: во временный файл рядом (`<имя>.adv-part`), `fsync`, затем `rename`. Существующий файл заменяется только после подтверждения в диалоге (стандартное поведение системного диалога). Если запись не удалась, временный файл удаляется.
4. Ограничение размера и типа: формат из закрытого списка (`raw`, `png`, `wav`, `obj`, `glb`), неизвестный формат даёт `wrong_kind` (как сейчас).
5. Обновить `GAPS.md` G-13 и `docs/SECURITY-AND-QUALITY.md`, чтобы текст совпал с кодом.

**Критерии приёмки**

- Тест функции записи: прерванная запись не оставляет файла под итоговым именем.
- Тест: путь, пришедший не из диалога (прямой вызов внутренней функции с произвольным путём), в публичную команду попасть не может (проверка сигнатуры: параметра `dest` нет).
- На вашей машине (NOT VERIFIED): диалог открывается на Windows и Linux, отмена диалога не даёт ошибки.

### A-04. Лимиты по форматам, потоковая распаковка, проверка слоя zlib

**Проблема (VERIFIED).** `Limits::default()`: `max_entries = 10 000 000` общий для всех счётчиков; `max_entry_size = 2 GiB`. `PakArchive::read` читает всю запись в `Vec` (до 2 ГиБ) и затем распаковывает zlib-слой до `max_inflated_size = 1 GiB`. Пик памяти на запись порядка 3 ГиБ. Степень сжатия проверяется только на слое ZIP, а на внутреннем слое zlib проверяется лишь абсолютный размер.

**Требования**

1. Разделить лимиты: `max_archive_entries` (паки, по умолчанию оставить большим, значение подобрать по реальному клиенту), `max_items_per_table` для форматов (БД, FSB, геометрия, анимации, `.loc`) на порядок меньше (старт: 2 000 000 для `.loc`, 1 000 000 для БД, 100 000 для остальных; числа подтвердить измерением на ваших данных, помечены NOT VERIFIED).
2. `PakArchive::read_to(entry, layer, &mut impl Write)` реализовать настоящим потоком (`io::copy` через `Take`) без промежуточного `Vec`, для `extract_entry` и `pack` (C-04). Версия с `Vec` остаётся для превью и ограничивается меньшим лимитом `max_preview_bytes`.
3. Проверка коэффициента на слое zlib: после начала распаковки сравнивать выход/вход; при превышении `max_ratio` для выхода выше `ratio_floor` прерывать с `Error::limit`.
4. Лимит суммарного объёма пакетной распаковки (`max_total_extract`, по умолчанию «без ограничения», но с предупреждением и опцией `--max-total`).
5. Все лимиты задокументировать в `limits.rs` (требование `missing_docs`) и в `docs/SECURITY-AND-QUALITY.md`; тест `defaults_cover_known_samples` дополнить проверками для каждого формата.

**Критерии приёмки**

- Тест: синтетическая запись «стоимость 1 МБ → 900 МБ после zlib» отклоняется по ratio, не выделив 900 МБ (проверка пика через ограниченный writer, который падает при записи свыше порога).
- Тест: потоковая распаковка записи 64 МБ не создаёт `Vec` такого размера (счётчик аллокаций в тестовом `Write` не нужен: достаточно того, что `read_to` не вызывает `read`).
- Все существующие тесты проходят без ослабления проверок (правило проекта: лимиты и тесты не ослабляются ради зелёной сборки).

### A-05. Коллизии имён на Windows при распаковке

**Проблема (VERIFIED).** Дубликаты в `PakArchive::open` ищутся регистрозависимо (`HashSet<String>`), а NTFS регистронезависим. `sanitize_for` может превратить разные имена в одно (`a?` и `a_`). При `--overwrite` одна запись молча затрёт другую.

**Требования**

1. В `extract` (пакетный режим) перед записью строить множество итоговых имён в нижнем регистре, после санитайзинга. Коллизия даёт `Outcome::Collision { path, with }` и запись пропускается (или переименование с суффиксом `~N`, режим `--on-collision=skip|rename|fail`, по умолчанию `rename` на Windows и `skip` с предупреждением на Linux, где коллизий в регистре нет).
2. В манифесте (C-01) хранится и исходное имя из пака, и итоговый путь на диске, чтобы упаковка вернула исходное имя.
3. Предупреждение в итоговой сводке: число переименованных.

**Критерии приёмки**

- Тест на любой ОС с параметром `windows: bool` (как `sanitize_for`): пары `A.txt`/`a.txt`, `a?`/`a_`, `CON`/`con.txt` дают различимые итоговые имена и отчёт.
- На вашей машине (NOT VERIFIED): распаковка реального клиента на NTFS не теряет ни одной записи (сумма записей = сумма файлов + пропущенные).

### A-06. Политика для `:` в именах и симлинков

**Проблема (VERIFIED).** `VPath` допускает `:` внутри имени, а `Session::split` отвергает любые `:`: такие записи видны ядру и недоступны через сессию (HYPOTHESIS: встречаются ли они в реальных паках, неизвестно). `resolve` идёт по симлинкам (`exists()`, `is_file()`).

**Требования**

1. Решить по данным: в `census` добавить счётчик записей, отвергнутых сессией, и найти ли такие на реальном клиенте. Если есть: принимать `:` в имени записей внутри пака, но не в именах папок файловой системы. Если нет: задокументировать и оставить.
2. Симлинки: выбрать и задокументировать одно из двух. Либо запрещать выход за `root` через `canonicalize` и `starts_with`, либо разрешать по явной опции. Тест: симлинк на внешнюю папку не читается без опции.

### A-07. Fuzz-таргеты

**Проблема (VERIFIED).** Каталога `fuzz/` нет, хотя главная поверхность атаки это парсеры чужих бинарных данных (G-12 это отмечает).

**Требования**

1. `fuzz/` на `cargo-fuzz` (версию проверить по crates.io на дату внедрения; в GAPS указана 0.13.2 от 2026-06-09).
2. Таргеты: `pak_open`, `pak_read`, `loc_parse`, `db_container`, `fsb_parse`, `geometry_parse`, `animation_decode`, `skeleton_parse`, `picture_decode`, `texture_convert`, `tdb_parse`, `packsinfo_parse`, `gamever_parse`, `vorbis_decode`, `ogv_header`.

5. Инвариант: паника на любом входе считается дефектом; исправление сопровождается регрессионным тестом (правило проекта).

## 4. Блок B. Факты из справочных проектов (только документация)

**Правила блока.** Источник: C# проект AllodsOnlineDatabaseUnpacker (без лицензии). ## 5. Общие требования и ограничения

1. **Слои.** Форматы разбирает и пишет только `adv-core`. `adv-session`, CLI и Tauri остаются тонкими оболочками (CLAUDE.md).
2. **Без `unsafe`**, `missing_docs` остаётся предупреждением, `clippy -D warnings` проходит.
3. **Ошибки значениями.** Библиотека не паникует на входных данных; все новые функции возвращают `Result`.
4. **Зависимости.** Новые только с согласованием владельца и релизом текущего календарного года. В спецификации сознательно не требуется ни одной: параллелизм через `std::thread::scope` и `std::sync::mpsc`, отмена через `AtomicBool`. Если будет решено использовать `rayon`, это отдельное согласование.
5. **Игровые данные не в репозитории.** Тесты строят крошечные синтетические входы. Образцы живут вне репозитория (`ADV_SAMPLES`).
6. **Windows и Linux.** Каждый путь кода проверяется на обеих ОС. Пути в манифесте всегда с `/` и в UTF-8; преобразование в нативные пути только на границе.
7. **Интерфейс на двух языках.** Любая новая видимая строка (прогресс, ошибки, подсказки, диалоги, пункты меню) добавляется в `web/src/i18n.ts` на русском и английском; `invariants.test.ts` и правило проекта это проверяют.
8. **Идемпотентность и безопасность записи.** Любая запись на диск идёт через временный файл и `rename`. Оригиналы не изменяются никогда: пакер отказывается писать в файл, который есть среди входных паков или лежит внутри каталога `data/Packs` исходного клиента без явного `--force-in-place`, а `--force-in-place` в первой версии не реализуется.

## 6. Блок C. Конвейер для модов

Исходные условия: `.pak` это обычный ZIP (VERIFIED в `docs/formats/pak.md`, подтверждено на образцах, открывают WinRAR и `unzip`). Записи могут быть `stored` или `deflate`, некоторые содержат дополнительный внешний слой zlib. `.loc` на диске это zlib-поток, под ним два варианта раскладки (VERIFIED, `docs/formats/loc.md`).

### 6.1. C-01. Массовая распаковка с манифестом

**Команда:** `adv extract-all <каталог-клиента-или-пак...> -o <папка> [--manifest <файл>] [--layer raw|decoded] [--on-collision skip|rename|fail] [--jobs N] [--filter <маска>] [--max-total <размер>] [--dry-run]`.

Существующий `adv extract` (один пак) сохраняется без изменений.

**Требования**

1. Вход: пак, папка с паками или каталог клиента. Порядок паков при совпадении путей определяется списком из `data/Packs` (если `packs.txt`/`packsinfo` доступны: VERIFIED, что `packsinfo.rs` существует; точный приоритет слоёв клиента NOT VERIFIED) либо явным порядком аргументов. Конфликт путей между паками фиксируется в манифесте (какой пак «победил», какие проиграли), без молчаливой перезаписи.
2. Параллелизм: пул из `--jobs` потоков (по умолчанию число ядер минус один, не больше 8). Каждый поток открывает свой экземпляр пака (не общий кеш), память ограничена потоковой записью (A-04).
3. Прогресс и отмена: колбэк прогресса (файлов, байт) и `Cancel` (A-02); при отмене незавершённые временные файлы удаляются.
4. Продолжение после прерывания: если манифест уже есть, записи с совпавшими размером и CRC пропускаются (режим по умолчанию, `--no-resume` отключает).
5. Итог: сводка (записано, пропущено существующих, переименовано, отклонено лимитами, ошибок) и код выхода: 0 без ошибок, 2 с пропущенными или переименованными записями, 1 при сбое.
6. `--dry-run` ничего не пишет, но выдаёт манифест и сводку.

**Схема манифеста (`manifest.json`, версия 1)**

```json
{
  "schema": 1,
  "tool": "adv",
  "tool_version": "0.1.45",
  "created_utc": "2026-11-19T12:00:00Z",
  "client": { "version": "18.0.00.05", "root_hint": "data/Packs" },
  "packs": [
    {
      "pak": "Bin_x64.pak",
      "pak_size": 123456789,
      "pak_sha256": "...",
      "entries": [
        {
          "path": "Bin/pack.rus.loc",
          "disk_path": "Bin/pack.rus.loc",
          "renamed": false,
          "zip_method": "deflate",
          "zip_level_hint": null,
          "zlib_layer": true,
          "size_packed": 1234,
          "size_unpacked": 5678,
          "size_inflated": 9012,
          "crc32": "89abcdef",
          "layer_written": "decoded",
          "status": "written"
        }
      ]
    }
  ],
  "conflicts": [
    { "path": "Bin/x.bin", "winner": "B.pak", "losers": ["A.pak"] }
  ],
  "skipped": [
    { "pak": "X.pak", "name": "...", "reason": "unsupported compression method" }
  ]
}
```

Правила схемы: поля никогда не удаляются внутри одной `schema`; новые поля необязательные; `disk_path` и `path` разделены, чтобы упаковка возвращала исходное имя (A-05); `zlib_layer` фиксирует факт внешнего слоя, `zip_level_hint` заполняется, если уровень удалось определить по флагам ZIP (иначе `null`).

**Критерии приёмки**

- Тест на синтетическом наборе из трёх паков с конфликтом путей: манифест фиксирует победителя, все файлы записаны, сводка корректна.
- Тест «прервать и продолжить»: вторая запуск после искусственной отмены дописывает недостающее и не трогает готовое.
- Тест на коллизии регистра (A-05).
- На вашей машине (NOT VERIFIED): распаковка всего клиента завершается, сумма записей сходится, время и пик памяти зафиксированы в отчёте.

### 6.2. C-02. `adv pack`

**Команда:** `adv pack <папка> -o <новый.pak> [--manifest <файл>] [--method store|deflate|auto] [--zlib-layer auto|always|never] [--level N] [--base <старый.pak>] [--filter <маска>] [--no-overwrite] [--dry-run]`.

**Требования**

1. **Отказ перезаписывать**: если `-o` существует, выход с ошибкой `output_exists`. Нет «тихой» замены, нет `--force-in-place` в первой версии.
2. **Определение метода и слоя для каждой записи** из манифеста (`zip_method`, `zlib_layer`). Если манифеста нет, правила по умолчанию: `.ogv` и уже сжатые форматы `stored`; текст и таблицы `deflate`; внешний слой zlib только для типов, где он встречался (`.loc`, `.bin` БД, `.bin` текстур, геометрия; список в таблице правил, а не в коде разбросанно). Таблица правил лежит в `docs/formats/pak.md` и тестируется.
3. **Детерминированность**: записи в порядке из манифеста, а без манифеста в лексикографическом порядке `path`; фиксированная метка времени (из манифеста или `1980-01-01 00:00:00`), никаких системных времён, прав доступа и случайных значений. Два запуска на одних входных данных дают побайтово одинаковый пак.
4. **Проверки перед записью**: допустимость путей через `VPath::parse` с теми же лимитами; запрет дубликатов путей, в том числе без учёта регистра; размеры в пределах `Limits`; отказ, если путь содержит имя, которое при распаковке было переименовано, а `disk_path` не сопоставлен с `path` через манифест.
5. **CRC32 и размеры** считаются при потоковой записи; запись ZIP64, если пак или запись не помещаются в классический ZIP (поведение клиента с ZIP64 NOT VERIFIED: по умолчанию предупреждать и просить `--allow-zip64`).
6. **Внешний слой zlib**: сжимать zlib с настраиваемым уровнем; побайтового совпадения с исходным сжатием не требуется и не гарантируется (HYPOTHESIS: исходный уровень неизвестен), критерий круга это совпадение **содержимого**, не байтов сжатия.
7. **Новый `.pak` только поверх существующего набора** через `--base`: режим пака-патча (C-03).
8. Запись во временный файл рядом и `rename`.

**Критерии приёмки**

- Тест: синтетическая папка → пак → распаковка → содержимое и CRC совпадают.
- Тест: детерминированность (два запуска, одинаковый SHA-256 файла).
- Тест: `output_exists`, дубликаты по регистру, запрещённые пути, слишком длинное имя дают понятные коды ошибок.
- Тест: пак открывается `PakArchive::open` без `skipped`.
- Проверка в клиенте (на вашей машине, NOT VERIFIED): новый пак принят игрой. До этого пункт M10 остаётся «PARTIALLY VERIFIED».

### 6.3. C-03. Режим «пак-патч»

Мод поставляется отдельным небольшим паком, который клиент накладывает поверх оригиналов (виртуальная ФС из всех `Packs`; в манифесте `game.version` перечислены `/data/Mods/...`, что говорит о существовании каталога модов, VERIFIED по `docs/formats/game-version.md`; порядок слоёв и приоритет NOT VERIFIED).

**Требования**

1. `adv pack <папка-изменений> --base <каталог-клиента> -o mod.pak`: включить только те файлы, которые отличаются от базы (по размеру и CRC32 декодированного содержимого) или отсутствуют в базе. В отчёте: добавлено, заменено, не тронуто.
2. Режим `--only-listed <файл>` для явного списка путей.
3. В отчёт попадает предупреждение, если файл меняет запись, чей путь повторяется в нескольких паках (конфликт слоёв, раздел 6.1).
4. Установка пака в каталог клиента не выполняется программой (она не трогает оригинальные данные); команда печатает рекомендуемое место и напоминает про правила игры (C-08).

### 6.4. C-04. Круговая проверка `adv verify-roundtrip`

**Команда:** `adv verify-roundtrip <каталог-клиента-или-пак...> [--scratch <папка>] [--keep] [--jobs N]`.

Последовательность: `extract-all` во временную папку → `pack` каждого исходного пака по манифесту → сравнение по записям (путь, размер после слоя, CRC32 декодированного содержимого, метод ZIP, наличие внешнего слоя).

**Критерии приёмки**

- Отчёт без расхождений на синтетическом наборе (автоматически, часть `cargo test`).
- На вашей машине (NOT VERIFIED): запуск на всём клиенте; расхождения перечисляются в `roundtrip-report.json`. Допускаются расхождения только в уровне сжатия (метод и содержимое совпадают).
- Команда не изменяет и не удаляет исходные паки (тест: хеш исходного файла до и после).

### 6.5. C-05. Запись `.loc` layout 1

Исходные факты (VERIFIED по `loc.md`): заголовок 16 байт (`0`, `sizes_pos`, `8`, `count`); таблица элементов из `count` записей по 12 байт (`pos`, `str_size`, `id`), где `pos` отсчитывается от начала самой записи; ключ в UTF-8 с нулевым байтом; таблица размеров из записей по 8 байт (`length`, `pos`); тексты в UTF-16 с нулевым терминатором и выравниванием по 4 байтам; `id` равен индексу записи.

**Требования**

1. API в `adv-core::loc`: `write_loc_v1(items: &[LocItemOut], limits: &Limits) -> Result<Vec<u8>>`. `LocItemOut` содержит ключ и текст. Внешний слой zlib добавляется отдельной функцией (уровень задаётся).
2. Пересчёт всех смещений и размеров с проверенной арифметикой (`checked_*`), отказ при превышении лимитов (число элементов, суммарный размер).
3. Две режима: «канонический» (собственная раскладка) и «по шаблону» (`--template <оригинал.loc>`): раскладка секций как в оригинале, чтобы неизменённый файл совпал побайтово.
4. Валидация перед записью: уникальность ключей (в самом большом образце есть одна повторяющаяся пара, поэтому дубликат ключа это предупреждение, а не ошибка, если он был в шаблоне), отсутствие `\0` внутри текста, длина текста в пределах `u32`.

**Критерии приёмки**

- Тест: `read_loc(write_loc_v1(x)) == x` по всем элементам на синтетических данных (используйте `build_v1` из тестовых утилит как эталон структуры).
- Тест: на неизменённом синтетическом файле режим «по шаблону» даёт побайтовое совпадение (определённая секция раскладки).
- Тест на границы: пустой список, один элемент, текст с эмодзи (суррогатная пара UTF-16), очень длинный текст, ключ на 1023 байта.
- На вашей машине (NOT VERIFIED): на трёх реальных файлах layout 1 (21 693, 150 587, 301 590 элементов) `read → write(template) → read` даёт совпадение; побайтовое совпадение либо подтверждено, либо расхождения описаны в `loc.md`.
- Сверка с `loc.compiler.exe` как с чёрным ящиком (по желанию, NOT VERIFIED): один и тот же вход через оба инструмента, сравнение результата после распаковки внешнего слоя.

### 6.6. C-06. Запись `.loc` layout 2 по шаблону

Исходные факты (VERIFIED по `loc.md`): 64-битный слепок памяти; `magic` отличается по версии клиента; дескрипторы по 16 байт (`length`, `offset`); 12 байт неизвестного назначения после таблицы (`u32 = 1`, затем `u64`, похожий на указатель); строки выровнены по 8 байтам и **дедуплицируются**; ключей нет, элементы адресуются индексом.

**Требования**

1. Первая версия пишет **только по шаблону**: `magic` и 12 неизвестных байт копируются из оригинала без интерпретации; изменяются только тексты. Без шаблона запись layout 2 не выполняется (код `template_required`), пока 12 байт не понятны.
2. Дедупликация строк обязательна и воспроизводит порядок размещения из оригинала (иначе клиент может отвергнуть файл, NOT VERIFIED).
3. Число элементов в изменённом файле должно совпадать с шаблоном (добавление и удаление строк в layout 2 не поддерживается: индексы связаны с базой).

**Критерии приёмки**

- Тест: `read(write(template, same_texts))` равен чтению шаблона; побайтовое совпадение на синтетическом файле.
- Тест: изменение одного текста меняет только его строку и, возможно, смещения последующих (проверка структурных инвариантов: все `base + offset + 2*length + 2 <= len`).
- На вашей машине (NOT VERIFIED): клиент принимает изменённый `pack.rus.loc` из `Texts_x64.pak`.

### 6.7. C-07. Экспорт и импорт `.loc`

**Команды:** `adv loc export <файл> -o <файл.tsv|.json> [--format tsv|json]` и `adv loc import <файл.tsv|.json> --template <оригинал.loc> -o <новый.loc>`.

**Требования**

1. TSV: столбцы `id`, `key`, `text`; экранирование `\t`, `\n`, `\r`, `\\`; кодировка UTF-8 без BOM; первая строка заголовок. JSON: массив объектов `{ "id": 0, "key": "...", "text": "..." }`.
2. Импорт сопоставляет строки по `id` (обязательно для layout 2, где нет ключей) и проверяет совпадение `key`, если он есть. Несовпадение даёт ошибку, а не молчаливую подмену.
3. Режим «только изменённые» (`--diff`): экспортировать/применять только строки, отличающиеся от шаблона; удобно для хранения перевода в системе контроля версий.
4. Предупреждение о разметке: тексты содержат теги (`<span>`, `<r name="..."/>`, `\r\n`); импорт проверяет, что набор тегов и подстановок в тексте не изменился (список расхождений, не блокирующий, ключ `--strict-markup` делает блокирующим).

**Критерии приёмки.** Круговой тест export → import без правок даёт файл, совпадающий по элементам с исходным. Поддержка очень больших файлов (порядка 300 000 элементов) потоково, без построения гигантского JSON в памяти.

### 6.8. C-08. Предупреждения и защита пользователя

1. Перед первой упаковкой и в справке команды выводится сообщение: правила игры и сервиса могут запрещать изменение клиентских данных; клиент или сервер могут проверять целостность файлов (в манифесте `game.version` есть размеры и контрольные суммы); последствия лежат на пользователе. Текст на русском и английском в `i18n.ts` (и в CLI тоже через те же ресурсы).
2. Проверка, что цель упаковки не лежит внутри `data/Packs` исходного клиента (защита от случайной порчи оригиналов).
3. Каждый созданный пак получает рядом файл `*.adv.json` с исходной информацией (версия клиента, из какой базы собран, список заменённых файлов, версия `adv`). Это помогает откатывать моды.

### 6.9. C-09. Правка баз ресурсов `.bin`: вне объёма

Причины (VERIFIED по `docs/formats/bin-db.md`, `docs/GAPS.md` G-08): образ данных (чанк 3) не декодируется, чанк исправлений указателей не разобран, раскладки структур для x64 нет. Любая запись без этого повредит базу. Предусловия, при которых пункт появится в плане: декодированный образ для `Texture`, `Geometry`, `LocalizedResources`; сверка с `types.xml` клиента; реконструкция чанка исправлений; круговой тест `read → write → read` на реальных файлах.

### 6.10. Связанное: `adv db check` (P2)

Команда проверки целостности ссылок: обходит ссылки между ресурсами (см. B-05), выводит список «битых» (ссылка есть, файла в паках нет). Использует то, что `adv db` уже читает контейнер (519 ресурсов, 1498 структур, 309 паков на главной `pack.bin`, VERIFIED по G-08), и полезна модмейкеру перед упаковкой.

| Клиент или сервер проверяет целостность файлов | вероятна | высокое | режим пака-патча, предупреждение (C-08), проверка на частном сервере или старой версии |

## 11. Откат

Все изменения идут отдельными версиями. Новые команды добавляются без изменения поведения существующих (`extract`, `list`, `tree`, `loc`). Внутренние изменения (A-01, A-02, A-04) защищены тестами и откатываются возвратом к предыдущему коммиту. Моды создаются в отдельных файлах и не трогают оригиналы, поэтому откат мода это удаление его пака.

## Приложение B. Коды ошибок новых команд

| Код | Когда |
|---|---|
| `output_exists` | цель упаковки уже существует |

| `template_required` | запись layout 2 без шаблона |
